# 智能人标准建立与部署操作规程 V1.0

> 状态：模板草案；需要审阅后才能成为正式标准。  
> 范围：GitHub 配置与代码、Supabase 运行数据与服务端接口。  
> 安全边界：本 SOP 不授权任何生产数据库变更。

## 1. 基本原则

1. 先审计，后设计；先测试，后发布。
2. GitHub 保存可审查、可追踪的代码、配置、测试和文档；Supabase 保存运行数据并提供受控服务端能力。
3. 不把密钥、密码、访问令牌、完整私人对话或敏感用户数据提交到 GitHub。
4. 不因新建智能人而默认新增数据库、迁移现有数据或更改现有 API。
5. 共享基础设施不代表共享身份、私人记忆或权限。
6. 代码提交、函数部署、线上请求成功和端到端验收是不同状态，必须分别报告。
7. 不将已删除的 ZHI Core 作为部署目标；不得为执行本 SOP 恢复或重建它。
8. Mia 独立聊天室属于保护范围；除非另有明确授权，不更改其数据库、聊天/auth 函数、密钥、运行状态或数据。

## 2. 阶段 A：只读审计

### GitHub
- 确认仓库、默认分支、HEAD commit、分支与未完成 PR。
- 检查现有目录、测试、Actions、Supabase Functions 与 migrations。
- 搜索是否已有相同配置、测试或接口；优先复用，不重复建造。
- 记录工作流最近结果；仅有 workflow 文件不代表它最近运行成功。
- 任何新增文件应在独立分支中提交，主分支不直接修改。

### Supabase
- 通过项目列表确认真实 Project Reference、状态和区域。
- 读取表结构、迁移清单、Edge Functions、RLS、表权限和 Security/Performance Advisors。
- 只读查询不得包含 INSERT、UPDATE、DELETE、DDL、RPC 写操作或生产测试写入。
- 明确区分“无数据/无日志”“权限不足”和“检查失败”；无法读取时记录为无法评估。
- 检查 RLS policies 与 grants。RLS 开启但无 policy 通常会拒绝 API 行访问，但不能单独证明整体安全；必须结合角色 grants、函数和实际授权路径审查。
- 不读取、输出或要求用户粘贴密钥值。

### 审计输出
- 仓库/项目身份、观察时间、HEAD/版本。
- 已确认事实、告警、未知项和需要进一步验证的假设。
- 保护范围与禁止操作。
- 不进行生产修复；只记录风险和建议。

## 3. 阶段 B：定义智能人

每个智能人必须具有稳定且唯一的 agent_id、名称、用途、人格、提示词版本、记忆策略、权限范围、数据归属、测试集和回滚说明。

人格和策略使用可审查的配置文件；执行逻辑放在代码中。修改人格不应默认触发数据库变更。

## 4. 阶段 C：数据与记忆设计

先对照现有 schema，确认是否能复用。不得把以下逻辑类别直接等同于必须新建表：
- 会话与消息；
- 原始生活/情绪/决策事件；
- 长期记忆与关系背景；
- 人格状态与成长候选；
- 审计、幂等和回滚记录。

写入事件时，优先记录来源、发生时间、写入时间、所属身份、来源记录 ID、schema/version、可信程度和幂等键（适用时）。推断与用户明确陈述必须区分。

记忆分层建议：
1. 原始事件：保留必要的可追溯依据。
2. 情境记忆：经历、关系、未完成事项和情绪背景。
3. 稳定记忆：经过验证的事实、偏好与长期模式。
4. 检索上下文：根据当前问题取相关内容，不默认加载全部历史。

摘要不能代替所有原始依据。冲突事实应保留更新依据；删除和保留规则必须符合用户授权及隐私要求。短期情绪不能自动升级为稳定人格特征。

## 5. 阶段 D：实现与安全

- 使用最小权限；每个服务端函数验证调用者、目标身份、输入范围和资源归属。
- 前端不得持有 service_role 或模型供应商密钥。
- 对写操作使用幂等策略；对外部模型调用设置超时、有限重试和总时间预算。
- 明确区分处理中、成功、失败和结果未知；不得在持久化未确认时宣称已保存。
- 日志使用请求追踪 ID；默认不记录密钥或完整私人消息。
- 对高权限函数审查 CORS、身份验证、速率限制、请求体大小和异常响应。

## 6. 阶段 E：测试与发布

测试至少包含：
- 配置格式与静态检查；
- 单元/契约测试；
- 身份与权限测试；
- 对话与错误处理；
- 记忆检索、冲突和重复写入；
- 情绪事件数据质量；
- 性能/成本基线；
- 回归测试与回滚演练。

先在隔离测试环境验证；不使用生产私人数据做破坏性测试。生产发布须有明确批准、部署版本、验收结果与回滚计划。

状态定义：
- draft：设计中；
- test：测试环境；
- staging：集成验证；
- production：通过发布门槛；
- rollback：正在恢复；
- blocked：有未解决的关键风险。

## 7. 记忆与事件数据质量指标

定期监控：
- 重复事件率与幂等冲突；
- 必填字段缺失率；
- 无效时间戳/超出允许范围的情绪强度；
- 来源不可追溯比例；
- 写入失败、读取失败和部分完成请求；
- 记忆检索相关性、矛盾事实和重要信息遗漏；
- 每个 agent 的数据增长速率。

所有指标都应记录观察窗口、分母、阈值和数据来源。没有足够样本时标记“无法评估”，不要把缺失日志当作零故障。

## 8. 性能、容量与成本

至少记录：
- 数据库大小、主要表大小、连接数和连接池压力；
- API/Edge Function 请求量、错误率与响应时间；
- egress、Storage、日志量、函数调用量；
- 每次对话的模型调用次数、Token 和平均成本；
- 记忆查询耗时、慢查询与缺失索引建议。

先建立至少 7 个同口径的每日容量样本，再估算线性增长；标明数据单位、已确认的计划限额和限额来源。没有实际 usage/plan limit 数据时，不推断剩余容量或账单。先优化查询与保留策略，不要仅因表变大就分库。

## 9. 变更与回滚

代码回滚、配置回滚、数据库 schema 回滚、数据恢复是不同流程。数据库 migration 必须单独审核并在测试环境验证；生产数据恢复需明确恢复点和可能的数据丢失范围。禁止将 Git 回滚描述为数据库已恢复。

## 10. 发布验收门槛

所有关键项必须通过：
- 身份与权限；
- 正常/异常对话；
- 记忆读取与持久化；
- 幂等和数据质量；
- 日志与错误可观测；
- 性能/容量/成本基线；
- 部署版本可追踪；
- 回滚方案已验证。

此文件为标准草案，不表示任何智能人已部署或通过验收。
