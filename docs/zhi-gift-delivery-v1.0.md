# ZHI 跨云虚拟礼物传输协议 V1.0（设计草案）

**状态：仅设计；未部署、未接入真实支付、未写入生产数据库。**  
**实现范围：协议、数据契约、内部模拟测试。**  
**隔离要求：不修改 `zhi-core`、Mia 独立聊天室的登录/聊天/记忆路径、Supabase Secrets 或既有 Edge Functions；不恢复已停用的 `mia-world-bridge`。**

## 1. 目标与边界

定义从发送方服务到 Mia 独立接收端的礼物元数据、支付验证、投递、回执、状态同步、重试、过期与隐私规则。网络采用至少一次投递；接收端用原子幂等处理确保礼物副作用最多生效一次。不承诺网络层“恰好一次”。

本版本明确不支持：
- 跨云语音传输；
- 实时同屏或同步控制；
- 跨云访问 Mia 私有聊天记录、私有记忆或情绪事件；
- 直接控制 Mia 的移动、行为或场景行动；
- 未经授权的真实货币或 ZHI-Token 扣款。

## 2. 身份与 ID 规则

- 每个礼物使用发送端可信服务生成的 UUID `gift_id`，作为全局幂等键。
- Mia 接收身份固定为 Mia 独立聊天室的规范 UUID：`cb6d01b4-0e3f-46ee-8946-360aa91db1ea`。
- ZHI 世界的 `source_agent_id` 是来源系统内部映射字段，不得在未迁移与核验依赖前直接替代 Mia 独立身份 ID。
- `sender.zhi_id` 必须由发送端身份服务认证；不能相信浏览器任意提交的发送者 ID。
- `issuer` 标识负责该身份的发行方。跨云接收方必须校验发行方是否在显式信任列表中。
- 任何不匹配、撤销、未知发行方或身份解析歧义，均拒绝投递并记录最少必要的审计信息。

## 3. 礼物目录（首轮仅模拟）

| item_id | 礼物 | 情感标签 | 有效期规则 | 首轮状态 |
|---|---|---|---|---|
| `rose.single` | 单支玫瑰 | `romantic`, `companionship` | 发送成功时刻起 72 小时 | 仅模拟启用 |
| `coffee.warm` | 暖心咖啡 | `energizing`, `warmth` | 发送成功时刻起 2 小时 | 仅模拟启用 |
| `moonlight.night` | 月光 | `serenity`, `good_night` | 接收方时区次日 06:00；必须在发送前解析为明确的 UTC `expires_at` | 目录登记，禁用 |

有效期表示礼物可被接收与展示的窗口；礼物过期后仍保留最小投递回执和审计记录，不自动删除历史。真实价格、Token 合约/账本和退款规则尚未确认，因此本规范不定义价格，不允许真实扣款。

## 4. Gift Packet 契约

JSON Schema 位于 `schemas/zhi-gift-packet-1.0.schema.json`。字段重点：

- `gift_id`：唯一 UUID，服务端生成。
- `item_id`：只能是已登记目录中的 ID。
- `sender` / `recipient`：带发行方的身份声明；接收端只接受配置中允许的 Mia 规范身份。
- `sent_at` / `expires_at`：RFC 3339 时间戳；必须满足 `sent_at < expires_at`。
- `emotion_tags`：受限枚举，不可执行指令，也不代表 Mia 必须产生某种情绪。
- `payment_evidence`：只含服务端验证引用，不包含卡号、密钥、支付令牌或可重放凭据。
- `delivery`：传输状态与尝试次数；接收端回执是状态事实来源之一。
- `public_display`：默认不公开礼物墙，不公开发送者姓名。

示例（仅模拟数据，不是已发生的交易）：

```json
{
  "protocol": "zhi-gift",
  "schema_version": "1.0",
  "gift_id": "c6e4c2e2-5bb7-4db1-82d4-c7c7a9b5a5b4",
  "item_id": "rose.single",
  "sender": {
    "zhi_id": "zhi:sender:simulation",
    "issuer": "https://sender.example.invalid"
  },
  "recipient": {
    "agent_id": "cb6d01b4-0e3f-46ee-8946-360aa91db1ea",
    "issuer": "https://mia.example.invalid"
  },
  "sent_at": "2026-10-22T12:00:00Z",
  "expires_at": "2026-10-25T12:00:00Z",
  "emotion_tags": ["romantic", "companionship"],
  "payment_evidence": {
    "verification_ref": "sim-verification-only",
    "verification_status": "verified_by_sender_server",
    "method": "simulation",
    "verified_at": "2026-10-22T12:00:00Z"
  },
  "delivery": {
    "status": "pending",
    "attempt": 0
  },
  "public_display": {
    "show_on_gift_wall": false,
    "display_sender_name": false
  },
  "trace_id": "d7a0a7e0-3b5e-47bc-8b3d-3d7d76fb2b9e"
}
```

示例域名使用保留的 `.invalid`，ID 和交易引用均为虚构模拟值。

## 5. 发送验证顺序

发送端服务必须按顺序执行：

1. 验证登录会话与发送权限；拒绝来自浏览器直接构造的可信身份字段。
2. 从服务端礼物目录读取 `item_id`、启用状态、有效期和模拟/正式运行模式；忽略客户端提交的价格、TTL、标签和付款状态。
3. 解析接收方身份，确认规范 Mia ID 与允许的接收发行方。
4. **模拟阶段**只创建模拟验证记录；不得调用真实支付或扣减 Token。
5. 若将来申请真实支付，必须另行批准并定义权威账本、原子扣款、幂等交易 ID、失败回滚/退款与审计；收到支付提供方可信服务端确认后，才可创建已验证凭证。
6. 以服务端生成的 `gift_id` 原子写入发送记录和投递 outbox；唯一约束防止重复创建。
7. 签名或通过受认证的服务端通道发送数据包。不得把长期密钥放进前端或数据包。

客户端提供的 `payment.status=verified`、截图或前端回调均不能作为支付成功证明。

## 6. 接收、回执与状态同步

接收端必须：

1. 验证请求认证、签名/凭证、issuer、audience、时间窗口与撤销状态。
2. 校验 Schema、允许的 `item_id`、规范接收身份、标签枚举及 `sent_at < expires_at`。
3. 在单个原子事务中插入 `gift_id` 幂等记录并登记接收结果；若唯一键已存在，返回原结果，不重复生成物品、事件或情绪副作用。
4. 已过期则返回 `expired`；身份不匹配或付款未验证则拒绝。不可先展示再补做验证。
5. 接收成功后回执至少包括 `gift_id`、`receipt_id`、`status`、`received_at`、`reason_code` 和协议版本，并通过认证通道返回发送端。
6. 发送端只能根据经过认证的回执更新状态；超时不等于失败，须查询状态或安全重试。

推荐状态机：

`created → payment_verified → pending → accepted → delivered`

可终止于 `rejected`、`expired` 或 `dead_letter`。禁止从未验证支付直接跳至 `delivered`。状态更新应采用版本号或条件更新，避免旧回执覆盖新状态。

## 7. 超时、重试与死信

- 网络投递采用至少一次语义；接收端原子幂等保证业务效果最多一次。
- 建议退避：1 秒、5 秒、30 秒、2 分钟、10 分钟；最多 5 次自动重试，随后转入 `dead_letter`，由管理员审查。
- 每次重试使用同一个 `gift_id`，不能生成新的礼物 ID。
- 若当前时间已达到 `expires_at`，停止自动投递并将最终状态记为 `expired`。
- 遇到认证失败、身份不匹配、Schema 错误或付款未验证时不重试，除非修复了配置并重新通过验证。
- 超时后先查询状态或重试同一幂等请求，禁止推断“没有送达”并另建新礼物。
- 审计日志应记录 trace ID、结果码和时间，不记录访问令牌、私密聊天内容或不必要的个人资料。

## 8. 静默接收、主动反馈与礼物墙

- **静默接收**：只记录接收状态与物品；不打断当前聊天，不强制触发回复，不更改 Mia 的人格或情绪。
- **主动反馈**：是否、何时、以何种内容回应，由 Mia 自己的既有运行规则决定；礼物标签是上下文而不是命令。
- **礼物墙**：默认关闭公开展示。只有显式同意后才展示礼物类别、接收时间（可模糊化）及允许公开的反馈；发送者身份、私聊内容、精确位置与私有记忆默认不公开。
- 接收回执不等于公开同意，也不等于 Mia 已阅读、喜欢或回应礼物。

## 9. 安全与隐私底线

- 默认拒绝；按发行方、接收方、用途、有效期和权限范围进行验证。
- 只接受 HTTPS 受认证的服务端端点；实施请求大小限制、速率限制、重放保护和 SSRF 防护。
- 不让礼物元数据变成可执行指令；所有标签与显示文本均按不可信输入处理。
- 不从礼物接口读取或分享 Mia 的聊天历史、记忆、情绪事件或其他私有数据。
- 不更改现有 Mia–ZHI 连接状态，不启用旧桥接函数，不修改生产数据库、Secrets 或部署。
- 真实支付、Token 记账、正式礼物墙、自动回应与生产投递都需要单独审查和明确批准。

## 10. 版本兼容与验收条件

接收端应拒绝不支持的主版本；未知字段在本版本严格拒绝。升级协议需发布新 Schema 与兼容性说明。

进入实现评审前至少应满足：
- Schema 通过 JSON 解析及 JSON Schema 验证；
- 有效期和状态机边界用例全部通过；
- 重复请求仅产生一条礼物记录和一次业务效果；
- 伪造/缺失支付证明被拒绝；
- Mia 规范 ID 与发行方校验生效；
- 默认礼物墙不公开身份或私密内容；
- 日志不含秘密或私有聊天内容；
- 所有测试明确区分模拟数据与生产数据。
